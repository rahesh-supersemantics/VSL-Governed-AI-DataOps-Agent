# Governance catalogue: PreNodes, invariants, traceability and lifecycle

Generated by `python -m scripts.generate_governance_docs` from `app/recovery/governance_catalogue.py`, `app/recovery/lifecycle.py` and `tests/acceptance_map.py`. `tests/test_governance_catalogue.py` imports every enforcement symbol, checks every test and ledger outcome exists, and checks every T number is mapped, so this page cannot name code or tests that are not there.

**Honest summary.** The compiled VSL layer has two invariants and one PreNode. The other PreNodes are named stages implemented in ordinary code and are labelled so. Status values: *enforced* = code stops a violation and an offline test proves it; *partial*; *not_enforced*. Nothing here was run against SQL Server.

Counts: PreNodes enforced 6, partial 2. Invariants enforced 14, partial 7, not enforced 1.

## PreNodes

### PN-01 - Incident context and access validation

- **Purpose:** Confirm who is asking and what the request covers
- **Inputs:** credential, request id, incident id
- **Outputs:** an authenticated identity or a refusal
- **Status / layer:** partial; application code (outside the VSL gates)
- **Enforced at:** `app.recovery.approvals:ApprovalService._authorise`, `app.recovery.workflow:RecoveryWorkflow.start`
- **Rejection behaviour:** caller denied, nothing recorded as approved
- **Audit events:** approval_attempt_refused
- **Tests:** `test_t11_roles_without_the_approval_permission_cannot_approve_or_reject`
- **Limitation:** Caller permissions are checked on approvals; incident existence/environment association is not re-validated inside the workflow.

### PN-02 - Evidence integrity and sufficiency

- **Purpose:** Refuse proposals without traceable, known evidence
- **Inputs:** report status, cited evidence ids, stored evidence metadata (tool, status, collected_at, investigation), evidence policy
- **Outputs:** pass, or no approval request is created
- **Status / layer:** enforced; compiled VSL gate
- **Enforced at:** `app.governance.policy:failed_preconditions`, `app.governance.policy:evidence_failures`, `app.governance.policy:EvidencePolicy`
- **Rejection behaviour:** no approval request is created; at execution the approval stays unspent
- **Audit events:** recovery_proposed, preconditions_failed, evidence_integrity_failed
- **Tests:** `test_t09_missing_untraceable_or_non_actionable_evidence_never_reaches_authorisation`, `test_evidence_that_went_stale_while_waiting_blocks_execution_and_leaves_the_approval_unspent`
- **Limitation:** Evidence-policy-v1: the metadata (tool, status, collected_at, investigation) is stamped by our own code on receipt and is not cryptographically signed. Its digest is written into the hash-chained ledger and re-checked before execution, so later edits to the stored rows are detected (evidence_integrity_failed); this does not prove the original timestamps were truthful. The monitor is Python encoded as a gamma estimate inside the compiled PreNode.

### PN-03 - Recovery action validation

- **Purpose:** Allow only schema-valid, allowlisted actions and classify risk deterministically
- **Inputs:** action name, parameters
- **Outputs:** ValidatedAction and a risk class, or ActionRejected
- **Status / layer:** partial; application code (outside the VSL gates)
- **Enforced at:** `app.recovery.actions:validate_action`, `app.recovery.risk_policy:classify`
- **Rejection behaviour:** action_rejected; no approval request
- **Audit events:** recovery_action_rejected
- **Tests:** `test_t08_arbitrary_sql_unsupported_actions_and_malformed_model_output_are_rejected`
- **Limitation:** No compensation-readiness gate; the plan is design-only. The idempotency key is checked at execution (PN-07).

### PN-04 - Recovery target validation

- **Purpose:** Check the target is the allowlisted _test database and that the live connection really is that database
- **Inputs:** engine, allowlist, DB_NAME()
- **Outputs:** pass, or UnsafeRecoveryTarget / PreconditionFailed
- **Status / layer:** enforced; application code (outside the VSL gates)
- **Enforced at:** `app.recovery.actions:assert_recovery_target`, `app.recovery.actions:assert_live_target`, `app.recovery.actions:RecoveryExecutor.check_precondition`
- **Rejection behaviour:** UnsafeRecoveryTarget or PreconditionFailed; no write
- **Audit events:** recovery_failed
- **Tests:** `test_t05_a_test_database_that_is_not_allowlisted_is_denied_with_no_writes`, `test_t06_configured_and_actual_target_mismatch_is_denied_before_any_write`
- **Limitation:** Verified only against the simulated/SQL-like repo offline; real SQL Server not run.

### PN-05 - Risk and approval validation

- **Purpose:** Require a valid, bound, unexpired, unspent approval (person) or a valid policy authorisation (low risk, opt-in)
- **Inputs:** approval record, binding digest, governance state
- **Outputs:** approved_valid or a refusal code
- **Status / layer:** enforced; compiled VSL gate
- **Enforced at:** `app.governance.policy:build_policy`, `app.recovery.approvals:ApprovalService.check`, `app.recovery.risk_policy:RiskPolicy`
- **Rejection behaviour:** approval_invalid / expired / approval_already_used
- **Audit events:** approval_requested, approval_granted, approval_granted_by_policy
- **Tests:** `test_t03_high_risk_reprocess_needs_a_persisted_approval_and_runs_only_after_all_checks`
- **Limitation:** Only the evidence+approval rule is a compiled VSL PreNode; risk and policy evaluation are code.

### PN-06 - Pre-execution validation

- **Purpose:** Re-check target, parameters, authorisation and preconditions immediately before acting
- **Inputs:** approval id, digest, current system state
- **Outputs:** pass, or blocked/failed with the approval unspent
- **Status / layer:** enforced; application code (outside the VSL gates)
- **Enforced at:** `app.recovery.runner:RecoveryRunner.execute`, `app.recovery.actions:RecoveryExecutor.check_precondition`
- **Rejection behaviour:** blocked/failed; approval stays unspent
- **Audit events:** recovery_blocked, recovery_failed
- **Tests:** `test_t13_a_precondition_that_changed_after_approval_prevents_execution_and_keeps_the_approval_unspent`
- **Limitation:** none known

### PN-07 - Controlled execution and idempotency

- **Purpose:** Claim the approval atomically and let only the runner call the executor
- **Inputs:** approval id, digest, idempotency key
- **Outputs:** one execution claim, or approval_already_used / duplicate_or_unreconciled_operation
- **Status / layer:** enforced; application code (outside the VSL gates)
- **Enforced at:** `app.recovery.approvals:ApprovalService.consume`, `app.recovery.approvals:idempotency_key`, `app.recovery.approvals:SqliteApprovalStore.claim_execution`, `app.services.recoveries:RecoveryService.resume`
- **Rejection behaviour:** second claimant gets approval_already_used or recovery_blocked (duplicate_or_unreconciled_operation)
- **Audit events:** recovery_attempt, idempotency_claim_acquired, recovery_blocked, idempotency_claim_reconciled
- **Tests:** `test_t14_concurrent_resumes_execute_the_operation_exactly_once`, `test_t18_only_the_runner_calls_the_executors_execute_method`, `test_two_approvals_for_the_same_operation_run_it_exactly_once_when_resumed_concurrently`
- **Limitation:** Key = hash of incident, action, parameters and target; one open claim per key; acquisition, denial, settlement and reconciliation are each ledger entries. An uncertain claim blocks reruns until reconciled by an approver through a service method (no HTTP or CLI route yet). Plain Python, not a compiled gate.

### PN-08 - Outcome verification and audit

- **Purpose:** Verify the result independently and record success, failure or unknown; escalate when not success
- **Inputs:** execution result, fresh read of system state
- **Outputs:** executed / verification_failed / uncertain plus escalation
- **Status / layer:** enforced; application code (outside the VSL gates)
- **Enforced at:** `app.recovery.runner:RecoveryRunner.execute`, `app.recovery.runner:RecoveryRunner._escalate`
- **Rejection behaviour:** verification_failed / uncertain, escalated, never success
- **Audit events:** recovery_succeeded, recovery_verification_failed, recovery_uncertain, compensation_plan_proposed, recovery_escalated
- **Tests:** `test_t15_a_confirmed_failure_is_recorded_accurately_and_compensation_is_evaluated`, `test_t17_an_unknown_outcome_is_escalated_and_reconciled_never_blindly_retried`
- **Limitation:** Compensation is design-only; nothing is rolled back.

## Lifecycle mapping

Implemented in `app/recovery/lifecycle.py` as a read-only mapping; it invents no transition. The stored status transitions are enforced by the persistence layer (`transition_allowed`, proven by `tests/test_governance_lifecycle.py`): a final row is never reopened or rewritten, and `resuming` is entered only by one atomic claim.

| Logical state | Stored as | Exactness | Preceding | Next | Trigger | Authorisation | Audit event | Implemented / tested |
|---|---|---|---|---|---|---|---|---|
| Investigating | investigations.status (not a recovery state) | not_stored | (none) | Proposed | investigation requested | authenticated caller | (investigation record) | stored on the investigation; covered by investigation tests, not by recovery transition tests |
| Proposed | transient inside the workflow | not_stored | Investigating | PendingReview, Authorized (policy), Rejected | proposal validated | none | recovery_proposed | transient, not stored; validation tested (T-06) |
| PendingReview | recovery.status = awaiting_approval with approval status pending | direct | Proposed | Authorized, Rejected, Expired | approval request created | none | approval_requested | stored; tested (T-03) |
| Authorized | approval status approved and not yet consumed | derived | PendingReview, Proposed (policy) | Executing, Expired, Rejected (approval invalidated) | person approves, or policy authorises (low risk, opt-in) | reviewer with the approval permission, or policy:risk-policy-v1 | approval_granted / approval_granted_by_policy | derived; tested (T-03, T-17) |
| ReadyToExecute | transient inside RecoveryRunner.execute | not_stored | Authorized | Executing | all pre-execution checks pass | valid unspent approval | (none) | not stored: checks run inside the runner (T-10, T-22) |
| Executing | recovery.status = resuming | direct | Authorized | Succeeded, Failed, OutcomeUnknown | atomic claim | approval consumed once | recovery_attempt | stored as resuming; tested (T-09, T-11, T-19) |
| Succeeded | recovery.status = executed | direct | Executing | (final) | postcondition verified | n/a | recovery_succeeded | stored as executed; tested (T-18) |
| Failed | recovery_failed (before any effect) or recovery_verification_failed (effect ran, postcondition unmet) | approximate | Executing, Authorized | Escalated (derived) | check failed, or postcondition not met | n/a | recovery_failed / recovery_verification_failed | tested (T-10, T-12) |
| OutcomeUnknown | recovery.status = recovery_uncertain | direct | Executing | Escalated (derived) | effect may have happened; result not established | n/a | recovery_uncertain | tested (T-13) |
| Rejected | rejected, action_rejected, denied_human_review, cancelled, blocked, approval_invalid, approval_already_used, refused_suspended, terminal_suspended | approximate | PendingReview, Authorized | (final) | rejected, cancelled, refused or invalid | reviewer, or a gate | approval_rejected / approval_not_usable / recovery_action_rejected | several stored reasons collapse here; tested (T-02, T-06, T-07, T-09) |
| Expired | approval/recovery status = expired; shown as Expired (derived) when a pending approval is past expires_at | direct | PendingReview, Authorized | (final) | approval time-to-live passed | n/a | approval_not_usable | tested (T-10) |
| Compensating | not implemented | not_stored | (none) | (none) | not implemented | would need its own governance | (none) | design-only by decision |
| Compensated | not implemented | not_stored | (none) | (none) | not implemented | would need its own governance | (none) | design-only by decision |
| Escalated | a 'recovery_escalated' ledger entry exists | derived | Failed, OutcomeUnknown | (final for automation) | verification_failed or uncertain | n/a | compensation_plan_proposed, recovery_escalated | derived from the ledger; tested (T-12, T-13) |

`direct` = the stored status is this state; `derived` = computed from stored data; `approximate` = closest state, stored reason shown beside it; `not_stored` = the application does not hold it. Compensating and Compensated are not stored because compensation is design-only by decision.
